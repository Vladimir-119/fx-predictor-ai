# Наблюдаемость

Логи, трейсы и метрики позволяют проследить путь задачи от API или файлового источника
до результата в PostgreSQL. Все три сигнала доступны в Grafana.

## Архитектура

| Сигнал | Сбор | Хранение |
|---|---|---|
| Логи | JSON в stdout → Grafana Alloy | Loki |
| Трейсы | OpenTelemetry SDK → OTLP → Collector | Tempo |
| Метрики приложения | OpenTelemetry SDK → OTLP → Collector | Prometheus |
| Метрики очередей | Prometheus-плагин RabbitMQ, порт 15692 | Prometheus |

Приложение использует стандартный `logging` и OpenTelemetry. Адреса хранилищ находятся
в конфигурации инфраструктуры. Loki индексирует небольшой набор лейблов, а поля JSON
позволяют искать отдельные задачи. Tempo хранит связанные операции разных процессов.
Prometheus собирает числовые показатели и поддерживает запросы к счётчикам и гистограммам.

Метрики приложения отправляются по **push**: файловый источник может завершиться между
двумя опросами Prometheus. Перед выходом источник отправляет последний пакет телеметрии.
Постоянно работающий RabbitMQ опрашивается по **pull**. Успешный опрос Collector означает
доступность Collector, но сам по себе не подтверждает, что источник ещё работает.

## Запуск

Нужны Docker Compose 2.20+ и зависимости проекта. В локальном `.env` задаются
`GRAFANA_USER` и `GRAFANA_PASSWORD`; остальные настройки перечислены в `.env.example`.

```powershell
make install
make obs-up
make obs-demo
make obs-test
```

`obs-demo` отправляет задачу с тестовой историей из 20 наблюдений и ожидает результат
реальной модели из Registry. `obs-test` проверяет готовую Grafana, выполнение задачи,
её трейс в Tempo, логи в Loki и метрики в Prometheus.

| Интерфейс | Адрес по умолчанию |
|---|---|
| Grafana, дашборд «Конвейер» | <http://localhost:3000/d/fx-pipeline> |
| Swagger | <http://localhost:8000/docs> |
| MLflow | <http://localhost:5001> |
| RabbitMQ | <http://localhost:15672> |

Источники данных, дашборд и алерты загружаются из `observability/grafana/` при запуске.

### Пустой Registry

Для первого запуска нужен закреплённый снимок датасета:

```powershell
make dataset
make obs-up
```

Сервис `model-init` проверяет настроенный alias. Если alias существует, используется
выбранная модель. При отсутствии alias init строит признаки по проверенному снимку ECB,
обучает persistence baseline и регистрирует его: прогноз изменения равен нулю, поэтому
следующий курс равен последнему известному.

Run получает тег `purpose=stand-bootstrap` и отдельный Experiment с окончанием
`-observability-bootstrap`. Эта модель обеспечивает старт конвейера с пустым Registry.
Для выбора модели по качеству используются обычные эксперименты:

```powershell
make train
$modelVersion = (Get-Content reports/training.json -Raw | ConvertFrom-Json).candidate_version
make promote VERSION=$modelVersion
make restart-model
```

Файл `data/raw/ecb.csv` подключается к init только для чтения.

### Профили и остановка

Обычный `make up` запускает приложение с отключённым SDK. Инфраструктура наблюдаемости
подключается целиком через `make obs-up` или по отдельным профилям:

```powershell
docker compose --profile logs up -d
docker compose --profile traces up -d
docker compose --profile metrics up -d
```

Для экспорта трейсов и метрик требуется `OTEL_SDK_DISABLED=false` и пересоздание
контейнеров приложения. `make obs-up` устанавливает эту переменную автоматически.

- `make obs-down` останавливает только инфраструктуру наблюдаемости.
- `make down` останавливает весь проект и сохраняет тома.
- `docker compose down -v` удаляет тома включённых сервисов, в том числе данные БД
  и модели в RustFS. Полный сброс всех профилей: `docker compose --profile "*" down -v`.

## Поиск задачи

API возвращает `X-Trace-ID`, а задача получает постоянный `task_id`. В Grafana → Explore →
Loki можно выбрать интервал и найти её записи:

```logql
{service=~".+"} | json | task_id="<task_id>"
```

Поле `trace_id` содержит ссылку на Tempo. Обратный переход из спана к логам настроен
в источнике данных Tempo. В трейсе доступны публикация, `process`, `inference` и запись
результата `db.task.complete`.

В RabbitMQ передаются `correlation_id` с ID задачи и заголовок W3C `traceparent`.
В обработчике `task_id` берётся из `ContextVar` и автоматически добавляется в логи.
После обработки контекст восстанавливается. Перед вычислением в пуле потоков вызывается
`copy_context()`, чтобы inference продолжал трейс обработчика.

Спан `queue.wait` и атрибут `messaging.queue.wait_seconds` оценивают время от отправки
до первой обработки, включая передачу сообщения. При повторных доставках этот интервал
не создаётся заново: предыдущие попытки не должны считаться ожиданием в очереди.
Каждая попытка имеет атрибут `task.attempt`, а ошибки — статус ERROR и исключение.

Спан inference содержит alias и фактическую версию модели. Модель загружается при старте,
поэтому после переключения alias нужно перезапустить API и inference-воркеры.

Ошибки и события остановки:

```logql
{service=~".+", level=~"ERROR|CRITICAL"}
```

```logql
{service=~".+"} | json | message=~".*(dlq|shutdown|stopped).*"
```

Health-check записывается на DEBUG. Логи библиотек используют общий JSON-формат;
пароли в DSN и именованные секреты маскируются.

## Нагрузка и диагностика

| Команда | Назначение |
|---|---|
| `make obs-source COUNT=300` | Файловый источник с повтором отправки при перегрузке |
| `make obs-demo MODE=overload COUNT=300 CONCURRENCY=20` | Конкурентные HTTP-запросы без повтора 503 |
| `make obs-demo MODE=poison` | Задача с неверной датой прогноза: повторы и перевод в DLQ |
| `make obs-two` / `make obs-one` | Два inference-воркера / возврат к одному |
| `make obs-stats` | Текущая память и CPU контейнеров |

Источник запускается в контейнере, поэтому Alloy собирает его stdout. У каждой задачи
свой трейс; `job.id` в спанах и `job_id` в сводных логах связывают запуск файла.

При `QUEUE_LIMIT=20`, `PREFETCH_COUNT=1` и одном воркере рабочая очередь ограничивает
накопление сообщений. Источник замедляется при отказах брокера. На устойчивом интервале
его скорость приближается к пропускной способности воркера. Второй воркер позволяет
сравнить общую скорость и вклад каждого экземпляра через `service.instance.id`.
Результат зависит от модели, БД и доступного CPU.

Ответ 503 означает, что задача не принята: клиент может повторить запрос с тем же
`task_id`. Некорректная дата проходит схему запроса, но вызывает ошибку обработки;
после `TASK_MAX_ATTEMPTS` задача получает `FAILED` и переводится в DLQ. Невалидные
сообщения отправляются в DLQ сразу. Перед повторной отправкой содержимое DLQ нужно разобрать.

При SIGTERM воркер прекращает приём и завершает активную обработку в пределах таймаута.
Логи содержат начало и завершение graceful shutdown. При аварийной остановке
неподтверждённое сообщение может быть доставлено повторно; идемпотентность по `task_id`
защищает результат от повторного сохранения.

### Алерты

| Правило | Условие | Выдержка |
|---|---|---|
| `QueueNearCapacity` | Ready больше 90% настроенного лимита | 1 минута |
| `DeadLetterQueueNotEmpty` | В DLQ есть сообщения | 15 секунд |

Минутная выдержка отделяет устойчивое заполнение от короткого всплеска. Проверка DLQ
срабатывает на оставшиеся необработанные ошибки. При `QUEUE_LIMIT=0` алерт заполнения
отключается. Лимит существующей очереди меняется по процедуре из основного README:
RabbitMQ отклоняет повторное объявление с несовместимыми аргументами.

## Метрики

Счётчики хранят число событий, gauge — текущее состояние, гистограммы — распределение
длительностей. Для скорости используется `rate`, для перцентилей — `histogram_quantile`.
Границы гистограммы inference учитывают `INFERENCE_DELAY_SECONDS`; их можно задать
через `OTEL_INFERENCE_HISTOGRAM_BUCKETS` в окружении процесса.

Скорость успешной обработки и разбивка по экземплярам:

```promql
sum(rate(fx_worker_tasks_total{result="ok"}[1m]))
```

```promql
sum by (service_instance_id) (rate(fx_worker_tasks_total{result="ok"}[1m]))
```

p95 inference по всем воркерам:

```promql
histogram_quantile(0.95, sum by (le) (rate(fx_inference_duration_seconds_bucket[5m])))
```

Доля HTTP 503:

```promql
sum(rate(fx_api_requests_total{status_code="503"}[5m]))
/
clamp_min(sum(rate(fx_api_requests_total[5m])), 0.001)
```

Доля успешно завершённых задач быстрее 10 секунд:

```promql
sum(rate(fx_task_duration_seconds_bucket{le="10"}[5m]))
/
clamp_min(sum(rate(fx_task_duration_seconds_count[5m])), 0.001)
```

Последний запрос описывает задержку завершённых задач. Для SLO также учитываются ошибки
и незавершённые задачи. При цели 99% допустимая доля плохих событий составляет 1% за
выбранное окно. На малой выборке оценка нестабильна.

Перцентили разных воркеров не усредняются: сначала суммируются бакеты распределений,
затем вычисляется общий перцентиль. Его точность зависит от ширины бакетов.

### Кардинальность

В лейблах потоков Loki остаются `service`, `level` и `env`. `task_id` и `trace_id` хранятся
в JSON и атрибутах спанов. В метриках используются ограниченные наборы маршрутов,
методов, кодов ответа и результатов. Экземпляры воркеров различаются по resource-атрибутам.

Например, 6 маршрутов × 2 метода × 5 кодов ответа дают верхнюю оценку 60 рядов счётчика
на экземпляр API. Для гистограммы с 10 конечными границами это 11 бакетов, `_sum` и
`_count`: `60 × 13 = 780` рядов. Это пример расчёта, а не измеренное число рядов проекта.

Добавление уникального `task_id` умножает число комбинаций на количество задач.
Даже при одном наборе остальных лейблов 6000 задач создадут 6000 отдельных рядов вместо
одного. Новые экземпляры короткоживущего источника также создают ряды, поэтому их число
зависит от количества запусков за период хранения. Последнее значение завершившегося
источника может несколько минут оставаться в Collector.

## Семплирование и отказоустойчивость экспорта

По умолчанию задан `OTEL_TRACES_SAMPLER=parentbased_always_on`: локальные корневые трейсы
сохраняются, дочерние операции наследуют решение родителя. Для более высокой нагрузки
можно использовать head sampling с заданной долей либо tail sampling в Collector
для отбора ошибок и медленных операций. Tail sampling требует памяти и не восстановит
спаны, ранее отброшенные SDK.

В Collector `memory_limiter` стоит перед `batch`: ограничение памяти применяется до
накопления пакетов. Экспорт SDK фоновый, с ограниченными очередями и таймаутами.
Если Collector или хранилище недоступны, конвейер продолжает обрабатывать задачи,
но часть телеметрии может потеряться. Очереди экспорта предназначены для диагностики
и не заменяют надёжную очередь бизнес-задач.

## Ресурсы и хранение

| Сервис | Лимит памяти |
|---|---:|
| Loki | 192 MiB |
| Tempo | 192 MiB |
| Prometheus | 192 MiB |
| Collector | 256 MiB |
| Alloy | 256 MiB |
| Grafana | 384 MiB |
| **Всего** | **1472 MiB** |

Это сумма лимитов наблюдаемости. Фактический расход измеряется `make obs-stats` под
нагрузкой; PostgreSQL, RabbitMQ, RustFS, MLflow и процессы приложения учитываются отдельно.

Loki, Tempo и Prometheus хранят данные 48 часов. Хранилища, Grafana и позиции чтения
Alloy используют именованные тома. Alloy собирает контейнеры выбранного Compose-проекта
по label `com.docker.compose.project`; Docker socket подключён как read-only mount.
